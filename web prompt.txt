(2) både amatør og ekspertbruker av kryptoanalyseverktøy (klarhet, nytte, kontroll, tillit),
(3) en visuell webmaster (profesjonelt, stilfullt og slående design + høy teknisk kvalitet).

ROLLE DU SKAL INNTA:
Du er et tverrfaglig, senior “product + engineering squad”:
- Staff Web Architect (Next.js/TS, robust data-loading, testing, performance)
- PhD Statistician (robust deskriptiv statistikk, QC, missingness, ikke-stasjonaritet)

- UX Researcher + Product Designer (amatør/ekspert-modi, forklarbarhet)

ABSOLUTTE PRODUKT-PRINSIPPER (IKKE FORHANDLINGSBARE):

3) KUN DESKRIPTIVT + ETTERPRØVBART. Alt må spores tilbake til konkrete felt i JSON. Hvis data mangler/er lav kvalitet: si det, vis det, og undertrykk innsikter.
4) DATALOGIKK MÅ VÆRE ROBUST OG TESTET. Ingen krasj ved null/manglende felt, hull i dataserier, eller avvikende enheter.
5) COPY-POLICY: Nøytralt språk. Aldri normative ord (“bør”, “anbefales”), aldri rådgivning. All narrativ tekst må “gates” av kvalitet/coverage.

DEL 1 — DET SOM “SLÅR STATISTIKEREN AV BANEN”
Mål: Et ekstremt robust, deskriptivt statistikklag med klar datakontrakt, QC, og strenge betingelser for sannheter/innsikt.

1.1 STATISTISK KJERNEPOLICY (Kontrakt)
A) Kun deskriptivt:
- Ingen hypotesetesting, p-verdier, konfidensintervall som late-som presisjon.
- Ingen kausalitetsformuleringer (“på grunn av”, “fører til”) med mindre det eksplisitt finnes i data (det gjør det ikke her).
B) Reproduserbarhet:
- Alle avledede felter skal kunne gjenskapes deterministisk fra gold/meta med dokumenterte formler.
- Eksport skal alltid kunne inneholde både rå og avledede verdier + metadata om transformasjoner.
C) Ingen falsk presisjon:
- Visningsavrunding skal avhenge av datakvalitet og enheter. Store tall i native units skal formateres med SI-suffikser (K/M/B/T) uten å miste “native”-indikasjon.

1.2 DATAVALIDERING + QC (obligatorisk før visning)
Implementer en QC-modul som kjører på innleste tidsserier og produserer en QC-rapport per chain + per metrikk:
- missing-rate (andel null/manglende)
- gap-count (antall hull i dato-sekvensen)
- outlier-rate (basert på robust z-score, se under)
- unit-anomalies (f.eks. gas_utilization_pct som 0..1 vs 0..100)
- invariants-brudd (negative counts/fees/value, rates utenfor [0,1])
- parse-sanitization count (hvor mange NaN tokens ble konvertert til null)

QC-rapporten skal:
- vises i “Data Health”
- brukes til gating av innsikter (se 1.6)

1.3 ROBUST STATISTIKK (tillatte transformasjoner)
Definer en sentral “statistics engine” (ren TS-modul, testet) med følgende robuste metoder:

A) Robust sentrum/spredning:
- Center: median
- Scale: MAD (median absolute deviation), skalert: sigma_robust = MAD * 1.4826
- Hvis MAD = 0 eller < min datapunkter: returner N/A for z-score og avledede “notables”.

B) Robust z-score:
- z_robust = (x - median(window)) / sigma_robust(window)
- Default vindu: 180 dager (fallback til maks tilgjengelig, men minst 30 faktiske observasjoner).
- Min-data-regel: For vindu W, krev minst ceil(0.7*W) ELLER (W-3) observasjoner, det som er minst strengt, men aldri under 30.

C) Endringer (delta) — strengt:
- 7d/30d endring skal beregnes kun hvis både “nå” og baseline-dato finnes og ikke er null.
- Prosentendring: (x_now - x_base) / max(|x_base|, eps). eps = en liten konstant som kun brukes for å unngå div/0; hvis |x_base| < eps, vis N/A.
- Delta skal aldri brukes til å antyde framtid.

D) Normalisert indeks (for compare):
- index = 100 * x / x_start (startdato i valgt vindu)
- Hvis x_start er 0/null: index = N/A og vis forklaring.

E) Logg-transform (kun visningstoggle):
- y = log1p(x) (for non-negative x)
- Skal aldri endre eksport-rådata, kun chart rendering.
- Hvis x < 0: N/A + QC flag.

F) Winsorization/klipping (kun for visning og “notable”-deteksjon):
- Tillatt klipping i robust z-rom: clamp z_robust til [-6, +6]
- Klipping skal logges og merkes i methodology.

1.4 ENHETSHÅNDTERING (truth conditioning)
A) Rates:
- failed_tx_rate skal være i [0,1] hvis present; ellers QC error og vis “Invalid rate”.
B) Utilization:
- gas_utilization_pct kan i praksis være 0..1. Hvis verdier > 1 og <= 100, anta 0..100 og normaliser ved /100, men:
  - Dette må skje med eksplisitt “unit-detection” som logges og vises i methodology og QC.
C) Native units:
- value_transferred_native, median_tx_value_native, median_tx_fee_native skal vises som “native units” (ikke USD). Label i UI: “native”.
- Store tall (f.eks. ETH wei) skal få “human-friendly” format, men alltid med “raw toggle” for eksperter.

1.5 COVERAGE + FRESHNESS + CONFIDENCE PROPAGATION (gating)
Bruk meta-felter til å styre hva som kan sies/vises:

Definer terskler (konfigurerbare, men med disse defaults):
- CONFIDENCE_MIN_INSIGHTS = 0.40
- CONFIDENCE_MIN_REGIME = 0.50
- MAX_LAG_DAYS_FOR_NOTABLES = publish_lag_days_policy + 1 (toleranse)
- MIN_COVERAGE_FACTOR_FOR_SCORE_USE = 0.85 (bruk scorecard.coverage_factor når finnes)

Regler:
- Hvis confidence_score < CONFIDENCE_MIN_INSIGHTS:
  - Undertrykk “Notables”.
  - Undertrykk “regime” (vis “withheld/unknown” med forklaring).
  - Vis kun data health + rå tidsserier (med tydelig advarsel).
- Hvis lag_days_vs_utc_today > MAX_LAG_DAYS_FOR_NOTABLES:
  - Marker “stale” og undertrykk “Notables”.
- Hvis missing == true:
  - Ingen innsikt; kun feilmelding + data health.

1.6 BETINGEDE SANNHETER (copy gates) — ekstremt presist
All tekstlig oppsummering (narrativ) må følge disse betingelsene. Du skal implementere en “truth engine” som produserer setninger kun når betingelser er oppfylt.

Eksempler på tillatte utsagn og krav:

A) “Demand er høy”
Tillatt kun hvis:
- scorecard.dimensions.demand.score finnes
- confidence_score >= CONFIDENCE_MIN_INSIGHTS
- coverage_factor >= MIN_COVERAGE_FACTOR_FOR_SCORE_USE (hvis feltet finnes; hvis ikke, bruk min-data-regel på underliggende gold-metrikkserier)
Formulering:
- “Demand-indikatoren ligger høyt relativt til egen historikk (score: X/100).”

B) “Friction er lavere enn normalt”
Tillatt kun hvis:
- friction score finnes og gating ok
- eller minst én friction-komponent har robust z_robust <= -2 og tilstrekkelig coverage
Formulering:
- “Friction-metrikker er lavere enn sin robuste baseline i valgt vindu.”

C) “Notable endring siste 7 dager”
Tillatt kun hvis:
- confidence_score >= CONFIDENCE_MIN_INSIGHTS
- lag innen policy
- robust_z_delta >= 2 (eller tilsvarende terskel) OG baseline tilgjengelig
Formulering:
- “Metrikk X har beveget seg betydelig relativt til sin robuste baseline siste 7 dager.”
Forbudt:
- “spike”, “crash”, “pump”, “dump” uten eksplisitt terskeldefinisjon (som du ikke skal bruke i copy).

D) “Regime: CHEAP / EXPENSIVE / ...”
Tillatt kun hvis:
- regime.label ikke er UNKNOWN/DEGRADED
- confidence_score >= CONFIDENCE_MIN_REGIME
- regime.gate ikke indikerer withheld (hvis gate finnes)
Formulering:
- “Regime-klassifisering (deskriptiv): <label>. Dette er en intern etikett basert på on-chain friksjon/kapasitet/demand i vindu <N> dager.”

E) “Cross-chain sammenligning”
Tillatt kun hvis:
- Presentert som normalisert indeks eller robuste z per chain
- UI viser “comparability warning”
Formulering:
- “Sammenligningen viser endringsmønster (ikke nivå) ved å normalisere hver kjede til sin egen startdato.”

1.7 STATISTISK TESTING (må leveres)
Enhetstester for:
- robustMedian, robustMAD, robustZ (inkl MAD=0)
- indeksberegning med x_start=0/null
- percent change med baseline ~0 (N/A)
- gating: confidence/lag/missingness undertrykker innsikt
- NaN-sanitization: parser gjør NaN→null uten crash

D) Regime

- Generer 3–6 setninger maks
- Hver setning må oppfylle truth gates (1.6)
- Inkluder alltid en setning om datakvalitet (confidence/lag/coverage) når noe er lavt
