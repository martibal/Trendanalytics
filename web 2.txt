

# CSS Blockchain Analytics — Complete Product & Dev Specification

**Document ID:** CSS-BA-ENDGAME-SPEC
**Version:** 1.0 (Final)
**Scope:** Full end-to-end system: pipeline → published dataset → web → API → UX → docs (methodology + wiki)
**UI Language:** English only
**Core constraints (absolute):** Price-agnostic; descriptive only; explainable; no forecasts; no advice; explicit dimensions; Basic+Advanced for everything; cloud-operable without local PC.

---

## 1) Executive Product Definition

### 1.1 Product promise (what the user gets)

A one-stop, price-agnostic blockchain trend analytics platform for **Bitcoin, Ethereum, Arbitrum, Base**, delivering:

* a **30-second landing snapshot**: “what matters now, in historical context”
* **deep chain dashboards**: “metric-by-metric, with context & methodology”
* a **Methodology** knowledge base: “how every number is computed, with caveats”
* a **Wiki** glossary: “terms & concepts, pedagogical”
* a consistent **API export layer** so customers can build their own analysis.

### 1.2 Pages (fixed: exactly 7)

1. `/` Landing — 30-second snapshot across all 4 chains
2. `/chains/bitcoin` — chain dashboard
3. `/chains/ethereum` — chain dashboard
4. `/chains/arbitrum` — chain dashboard
5. `/chains/base` — chain dashboard
6. `/methodology` — full computation transparency
7. `/wiki` — glossary and learning resources

### 1.3 Non-negotiable content rules

* No price data, no price charts, no price proxies
* No predictions, no “likely”, no “expect”, no “bull/bear”, no “should”
* Only descriptive statements, always paired with explicit caveats when applicable
* Every metric shown must have: **What / How / Why / Value**
* Every view shows explicit dimensions: time window, coverage, freshness/lag, confidence, units/transforms, historical reference.

## 2) System Architecture (Cloud-first, maintainable)

### 2.1 Components

**A) Pipeline (batch)**

* Triggered initially by GUI button (`css_gui_pipeline`).
* In production, runs scheduled (cron / cloud scheduler) daily.
* Outputs artifacts into `data/published/v1`.

**B) Published dataset contract (static, web-ready)**

* Single immutable dataset per run: `dataset_id`, `revision_id`.
* Contains gold/meta/derived + landing descriptors.

**C) Web app (Next.js)**

* Consumes only `public/data/published/v1/**`.
* Provides interactive analytics via server routes:

  * `/api/series` for timeseries assembly from daily JSONs
  * `/api/summary` for deterministic interpretation & statistics
  * `/api/export/*` for customer API export

**D) Storage / hosting**

* Static files served by CDN/object store or web server.
* API runs in same Next deployment or separate serverless endpoints.

### 2.2 Cloud deployment requirement

A deployment must be possible with:

* Pipeline job container (Python + PowerShell support if kept, but should be runnable in Linux too if possible; Windows-only is allowed only if required by toolchain).
* Web container.
* Shared object storage or artifact volume for `data/published/v1` that web reads from (or publish step syncs into web’s public directory).

**Accepted cloud patterns:**

1. **Monorepo single host**: pipeline writes to shared disk; Next serves public from same disk.
2. **Artifacts to object storage**: pipeline uploads `published/v1`; web serves via CDN path `/data/published/v1`.
3. **CI publish**: pipeline runs in CI, commits artifacts to release bucket, web reads it.

**Mandatory:** local PC must not be required for runtime.

## 3) Data Contract (Published Dataset is the only truth)

### 3.1 Required file structure

Web and API must assume:

* `/data/published/v1/dataset.json`
* `/data/published/v1/landing/index.json`
* `/data/published/v1/landing/<chain>/hero.json`
* `/data/published/v1/{gold,meta,derived}/<chain>/manifest.json`
* `/data/published/v1/{gold,meta,derived}/<chain>/YYYY-MM-DD.json`
* `/data/published/v1/{gold,meta,derived}/<chain>/latest.json`
* `/data/published/v1/{gold,meta,derived}/<chain>/last{7,30,90,180,365}d.json`

### 3.2 Manifest contract (required fields)

Each `{genre}/{chain}/manifest.json` must contain:

* `asof` (YYYY-MM-DD)
* `available_days[]` (sorted)
* `available_days_count`
* `windows_supported[]`
* `files.latest` and `files.windows.{w}` existence flags

**Web must treat manifest as source of truth for:**

* “latest date”
* “range of selectable start dates”
* coverage (missing days)

### 3.3 Verified gold fields (minimum expected)

From your existing gold samples, web must support these keys when present:

* `tx_count_daily` *(int)*
* `median_tx_fee_native` *(float)*
* `avg_block_time_sec` *(float)*
* `block_count_daily` *(int)*
* `gas_utilization_pct` *(float 0..1 or 0..100 depending on pipeline; web treats as 0..1 unless meta says otherwise—see units rules)*
* `failed_tx_rate` *(float 0..1)*
* `unique_active_addresses` *(int/float; may be null)*
* `median_tx_value_native` *(float; may be null)*
* `value_transferred_native` *(float; may be null)*

### 3.4 Verified derived fields (minimum expected)

From your derived daily samples:

* `derived.meta_confidence.confidence_score` *(float 0..1)*
* `derived.metrics.<metric>__ma7`
* `derived.metrics.<metric>__ma30`

### 3.5 Meta fields (required behavior even if missing)

If meta contains:

* z-score / percentile / long-run distribution stats per metric,
  web will show them.
  If meta does **not** contain them, web must:
* show “Not available” in Advanced
* never crash, never show NaN as UI text (use “—”)

## 8) Live Web Computation (from daily JSON, cloud-safe)

### 8.1 Goal

User can select any start date; end = latest.
All displayed values must update:

* chart points (daily)
* MA7/MA30 (from derived daily)
* confidence score
* z/percentile if meta supports
* interpretation text

### 8.2 Why not fetch hundreds of daily files directly in browser

* Too many requests (performance, cost, failure rate)
* Hard to cache efficiently client-side

### 8.3 Required solution: Next API aggregation layer

Implement server routes that read static published files and return aggregated outputs.

#### 8.3.1 `/api/series` (required)

**Input (query params):**

* `chain` = bitcoin|ethereum|arbitrum|base
* `metric` = one of the gold metric keys
* `start` = YYYY-MM-DD
* `end` = omitted → server uses gold manifest `asof`

**Output (JSON):**

* `dataset_id`, `revision_id`
* `chain`, `metric`
* `start`, `end`
* `rows[]` each:

  * `date`
  * `daily` (from gold daily file)
  * `ma7` (from derived daily file metric__ma7)
  * `ma30` (from derived daily file metric__ma30)
  * `confidence` (from derived meta_confidence.confidence_score)
  * `z` (meta if available else null)
  * `percentile` (meta if available else null)
* `coverage`:

  * `expected_days`, `present_days`, `missing_days[]`, `nonNull_ratio`
* `freshness`:

  * `asof`, `lag_days` (computed from today)

**Mandatory rule:** MA7 and MA30 must come from **derived daily** if present.
Fallback compute rolling mean server-side only if derived missing for that date, with:

* `ma_source="fallback_computed"` included in row for those dates.

#### 8.3.2 `/api/summary` (required)

**Input:**

* `chain`, `metric`, `start`, `end`

**Output:**

* `current`:

  * latest daily, latest ma7, latest ma30
* `period`:

  * mean daily, median daily, stdev daily
* `trend`:

  * slope of ma30 over period (linear regression)
  * label: Rising/Falling/Flat
  * strength: Weak/Moderate/Strong by |slope| normalized by period stdev
* `volatility`:

  * coefficient of variation of daily (stdev/mean absolute)
  * label: Stable/Variable/Highly variable
* `level`:

  * classification based on historical reference (meta percentile if exists else period-only bands)
* `confidence`:

  * mean confidence over period + latest
* `caveats[]`:

  * missing days, low coverage, lag statement
* `interpretation`:

  * `basic`: exactly 2 sentences
  * `advanced`: bullet list strings

### 8.4 Caching (mandatory)

Server routes must cache by:

* `dataset_id + chain + metric + start + end`
  When dataset changes, cache invalidates automatically.

## 9) Interpretation System (Basic + Advanced for every metric)

### 9.1 Deterministic interpretation (no generative variability)

Interpretation must be produced from `/api/summary` outputs using fixed templates.

### 9.2 Basic template (exact format)

Sentence 1:

> “Over the selected period, **{metric_name}** has been **{level_label}**, with a **{trend_strength} {trend_label}** trend and **{vol_label}** variability.”

Sentence 2:

> “This means **{plain_meaning_translation}**, and the changes are **{stability_translation}** rather than isolated outliers.”

If caveats exist, append short note below (not extra sentence):

> “Data notes: {top_caveat}.”

### 9.3 Advanced template (fixed bullets)

* Window: `{start} → {end}` (`{present_days}/{expected_days}` days)
* Freshness: `as-of {asof}`, lag `{lag_days}` day(s)
* Current: `daily={x}`, `ma7={y}`, `ma30={z}`
* Trend method: “Linear slope of MA30 over window; strength normalized by daily dispersion”
* Vol method: “Daily coefficient of variation over window”
* Confidence: “Mean confidence over window + latest”
* Missingness: “Missing days: N; non-null ratio: R”
* Meta context: “z-score/percentile available: yes/no”
* Caveats: list

### 9.4 Plain-language translations (deterministic mapping)

* `level_label` mapping:

  * Extreme: percentile ≥ 95
  * Elevated: 80–95
  * Typical: 20–80
  * Low: ≤ 20
  * If percentile missing: compute relative to chain’s last365d distribution using rank.

* `trend_label`:

  * Rising if slope > +T
  * Falling if slope < −T
  * Flat otherwise
  * Threshold T = 0.05 * (stdev_daily / max(1, window_days)) normalized

* `vol_label`:

  * Stable if CV < 0.25
  * Variable if 0.25–0.60
  * Highly variable if > 0.60

* `plain_meaning_translation` (examples per metric):

  * tx_count_daily: “the network’s day-to-day activity level has been {higher/lower/about typical} compared to its usual range.”
  * gas_utilization_pct: “blocks have been {more/less} full than usual, indicating {higher/lower} execution demand relative to capacity.”
  * median_tx_fee_native: “typical transaction cost has been {higher/lower/about typical} compared to recent history.”
  * failed_tx_rate: “a {higher/lower} share of transactions failed than usual, reflecting {more/less} execution friction.”
  * avg_block_time_sec: “block production cadence has been {slower/faster/about typical}.”
  * block_count_daily: “block output has been {lower/higher/about typical}.”
  * unique_active_addresses: “participation breadth has been {narrower/broader/about typical}.”
  * value_transferred_native: “settlement volume has been {higher/lower/about typical} in native units.”

* `stability_translation`:

  * Stable: “relatively smooth and persistent”
  * Variable: “changing meaningfully week-to-week”
  * Highly variable: “dominated by sharp swings”
