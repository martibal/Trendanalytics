3) Hva som skjedde underveis (viktige problemer + løsninger)
Problem A: Next.js prerender/build-feil (“workUnitAsyncStorage”)

Vi fikk repeterende build-feil i next build:

Invariant: Expected workUnitAsyncStorage to have a store. This is a bug in Next.js.
Feilen trigget ved prerender av sider som /internal/catalog, /, /_global-error, /_not-found.

Løsning vi gikk for (minste invasive endring):

Flyttet “tung UI + fetch” til Client Components (f.eks. CatalogClient, HomeClient).

Lot page.tsx for relevante ruter bli en tynn Server wrapper som kun rendrer client-komponenten.

La på eksplisitte Next-flags på noen pages for å unngå caching/prerender issues:

export const dynamic = "force-dynamic";

export const fetchCache = "force-no-store";
(Dette er for å tvinge runtime behavior som ikke forsøker å prerendre / cache på måter som trigget invariant-bug.)

Problem B: TypeScript props mismatch i MetricChart

Feil:

Property 'chain' does not exist on type MetricChartProps
Årsak: MetricChart tar rows + metricKey, ikke chain.

Løsning:

I chain-siden bygges rows (timeseries) for riktig chain og sendes inn som:

<MetricChart rows={rows} metricKey={m.key} />

Problem C: “Module not found: Can't resolve './CatalogClient'”

Årsak: Filnavn/import mismatch.

Løsning:

Sørget for at src/app/internal/catalog/CatalogClient.tsx eksisterer og at page.tsx importerer korrekt:

import CatalogClient from "./CatalogClient";

Problem D: Node/npm rot (Windows EPERM, “next not recognized”, nvm)

Vi traff EPERM unlink lightningcss...node under npm ci (typisk Windows file-lock/AV).

Vi fikk også situasjoner der next ikke var i PATH etter at node_modules ble slettet.

Vi testet NVM for Windows; fikk PATH/symlink issues, måtte legge til $env:NVM_SYMLINK i PATH for at node skulle finnes.

Vi endte med Node v22.11.0 i en periode, men hovedpoenget: vi ønsker ikke OS-endringer fremover; kun minimale kodeendringer.

Status nå:

npm run build kjører og fullfører (vi har skjermbilde der build lykkes og lister routes).

Det kom fortsatt en warning om at Next “workspace root may not be correct” pga flere lockfiles. Dette er en hygiene-ting vi kan adressere senere (evt. turbopack.root i next config eller rydde lockfile-lokasjoner).

6) Hva som er neste trinn i utviklingen (prioritert)

Stabilisere build uten OS-endringer

Målet er at npm run build alltid fungerer på Windows uten nvm-triksing.

Vi må unngå imports som trekker inn Next server internals i client eller prerender.

Minimal endring i struktur; kun nødvendige patches.

Harde opp datadimensjoner i UI

For hver metrikk/regime: eksplisitt vise:

window (last365d)

chain coverage

freshness/lag (BTC/ETH vs Base/Arb)

enhet/scale (sec, wei, rate 0..1 osv.)

transformasjoner (MA7/MA30)

referanse (egen historikk, percentiler osv.)

Utvide regimes

Activity regime er på plass (TX + Address participation).

Fee/Capacity regime er på plass (Fees + gas utilization).

Neste regime å vurdere: “Reliability / Execution” (failed_tx_rate), eller “Value flow” (value_transferred_native + median_tx_value_native), men uten normativ tolkning.

Notables: gjøre kriterier helt eksplisitte

Definisjon av “notable” basert på:

avvik i forhold til historisk distribusjon (percentile/zscore-ish men forklarbart)

persistens (uavbrutt N uker)

Alltid Basic/Advanced og alternative forklaringer.

Catalog hygiene

“Declared-but-not-observed” panel skal være robust, men må ikke blokkere build.

Rydde opp i warnings: “metric exists but all missing” (kan vente, men pipeline bør merkes).

Unit badges: definere canonical mapping pr metric_id (ikke bare heuristikk).
