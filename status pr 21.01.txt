Crypto Chain Status – Detaljert readme.txt (pinlig nøyaktig)

Dato: 2026-01-21
Status: Nettstedet kjører lokalt via GUI (CSS GUI Pipeline) og viser data. Det er fortsatt logikk-/produkt-uklarhet rundt “DEGRADED/LIMITED SIGNAL” for Base/Arbitrum, og noe forvirring rundt hvilken versjon av filer som faktisk er i bruk (cache/build-versjonering).

1) Hva prosjektet er

Dette prosjektet består av:

En pipeline som produserer JSON-data (meta/gold) pr chain og tidshorisont.

Et statisk nettsted (web/) som leser JSON fra /data/... og rendrer:

Market overview

Top movers

Chain-spesifikke dashboards (graf + stats + drivere)

“Metrics Lab” og andre sider (delvis)

Målet er at alt skal være:

Enkelt å vedlikeholde

Enkelt å feilsøke

Enkelt å “løfte” til sky/produksjon (statisk hosting + data-folder)

2) Hvordan det kjøres i praksis (operativt)
2.1 GUI (CSS GUI Pipeline)

GUI har to knapper:

Kjør pipeline (oppdater alt)
Kjører PowerShell pipeline-script som:

oppdaterer data

bygger web dist

starter en lokal statisk server

Åpne nettsiden
Åpner nettleser mot lokal server (typisk http://127.0.0.1:8000/index.html)

2.2 Lokal statisk server

Serveren server typisk innhold fra D:\CSS\main\web\ (eller web\dist\, avhengig av pipeline) på port 8000.

3) Filstruktur: hva finnes hvor (oversikt)
3.1 Data (serveres under /data/)

Data ligger i praksis i prosjektet under en data-rot (f.eks D:\CSS\main\data\...) og kopieres/eksponeres til web:

Viktige URL-er som nettsiden forventer:

/data/manifest.json

/data/css_json/<chain>/<windowfile>.json

/data/css_json_meta/<chain>/<windowfile>.json

Der:

<chain> = bitcoin | ethereum | base | arbitrum

<windowfile> = typisk last30d.json, last90d.json, last180d.json, history.json, latest.json (varierer litt mellom versjoner)

3.2 Web (statisk nettsted)

web/ inneholder:

index.html (inngang, loader CSS + app.js)

assets/css/styles.css (styling)

assets/js/app.js (router + init)

assets/js/flags.js (konfig, chains, terskler)

assets/js/data_loader.js (fetch/cache + endpoint mapping + windows)

assets/js/stats.js (rollingMean/robustZ/percentileRank osv)

assets/js/charts.js (renderLineChart)

assets/js/views/landing.js (market overview)

assets/js/views/chain.js (chain dashboard)

ev. andre views: metrics lab, methodology, integration osv

3.3 Build-output

web/dist/ er bygget output som skal kunne hostes statisk.
Build kopierer:

assets -> dist/assets

index.html -> dist/index.html

data (eller peker på data-rot via serveren)

4) Målet med nettsiden (produktnivå)

Crypto Chain Status skal gi en “operatøroversikt” over on-chain aktivitet:

Regime (f.eks STABLE, CHEAP, TIGHT osv) per chain

Confidence (kvalitet på signal)

Demand/Friction/Capacity (forståelsesramme)

Top movers (statistisk sterkest avvik vs historikk)

Chain-side med:

Fokus-metric (dropdown)

Window-knapper (30/90/180) som faktisk endrer serie og recompute

Chart (daily + MA7 + MA30)

Latest/Change/Rolling/Position

Drivers-tabell (“deep”)

5) Hva som var feil og hva som ble fikset (historikk)
5.1 “Åpne nettside” gav Not Found / blank

Symptom:

GUI åpnet http://127.0.0.1:8000/

Nettleser viste {detail:"Not Found"} eller blank side

Tiltak:

Endret server/URL i GUI til å åpne .../index.html

Endret build/struktur så dist inneholder index.html og assets

Resultat:

Side åpner.

5.2 Pipeline-feil: “Missing required script: web\build.py”

Symptom:

full_pipeline.ps1 feilet med at D:\CSS\main\web\build.py manglet

Tiltak:

La til web/build.py som pipeline forventer

Resultat:

Pipeline kunne fortsette.

5.3 Pipeline-feil: PowerShell “Count cannot be found on this object”

Symptom:

Under “Build FEATURES daily parquet” feilet pipeline på .Count

Tiltak:

Patch full_pipeline.ps1 slik at den håndterer $null/ikke-array korrekt

Resultat:

Pipeline kjørte videre.

5.4 Web: “Loading…” hang, eller JS-feil i console

Symptomer som kom i ulike runder:

“Loading chain data...”

“Cannot read properties of undefined (reading 'length')”

percentileRank importfeil (export manglet)

404 på favicon eller css

Tiltak:

Oppdatert stats.js exports slik at det matcher imports

Forbedret defensiv sjekking i views

Lagt inn cache-busting (querystring ?v=) for å unngå gamle filer i browser

Lagt inn favicon eller ignorert 404

Rettet CSS-path (assets/css/styles.css) og sikret build kopierer den riktig

Resultat:

Side rendrer (ikke lenger loading).

CSS fungerer når assets path/build er riktig.

5.5 JSON parse-feil: “NaN is not valid JSON”

Symptom:

Console: Unexpected token 'N' ... "NaN" ... is not valid JSON

Skjedde etter at historikk ble tatt inn mer komplett

Årsak:

Pipeline eller build skrev NaN i JSON (ikke lov i JSON-standarden)

Tiltak:

Oppdatert build-script til å sanitere JSON: NaN, Infinity, -Infinity -> null (eller string) før web leser det

Resultat:

JSON blir parsebart i browser.

5.6 Window-knapper (30/90/180) endret ingenting

Symptom:

Valg av 90/180 ga ingen endring i graf eller stats

Årsak:

chain view lastet alltid last30d.json eller samme datasett uansett window

Tiltak:

Endret chain.js og data_loader.js slik at:

window-knappene faktisk påvirker hvilket JSON som lastes (last30d/last90d/last180d)

stats re-beregnes på window change

Resultat:

Windows endrer nå graf/stats (minst for BTC/ETH).

6) Hva vi prøver å fikse akkurat nå (nåværende problem)
6.1 Problem A: Base/Arbitrum viser “UNKNOWN/DEGRADED” eller “LIMITED SIGNAL” selv om historikk finnes

Symptom:

Market overview: Base/Arbitrum står som UNKNOWN/DEGRADED eller LIMITED SIGNAL

Tekst sier “confidence below threshold; regime withheld…”

Samtidig kan “Confidence” være høy (97%/100%)

Brukerobservasjon:

Det finnes full historikk i data-mappen for både meta og gold over >1 år. Derfor burde ikke “manglende data” gi degradering.

Sannsynlig årsak (viktig):

Det er to forskjellige konsepter som blandes:

Data coverage (har vi nok datapunkter til å beregne robust z, MA, percentile osv?)

Regime publish policy (tillater produktet å publisere regime når signalet er for svakt eller modellen ikke er kvalifisert for L2?)

Vi har tidligere hatt logikk der “confidence under threshold” setter regime til UNKNOWN/DEGRADED.

Senere ble det forsøkt å endre til “LIMITED SIGNAL” for å tydeliggjøre at data kan finnes, men regime withheld.

Men: UI viser fortsatt en tekst som sier “low confidence” samtidig som confidence i tall er høy, som gir motsigelse.

Dette er nå hovedkilden til forvirring.

6.2 Problem B: Versjons-/cacheforvirring: hvilke filer er faktisk i bruk?

Symptom:

Build-id viser 2026-01-20.v4 i UI.

Men det var flere runder med filer (v5, v6, v7 osv).

Bruker opplever at endringer “ikke slår inn” selv om filnavn er riktig.

Årsaker:

Browser cache (selv om ?v= ble forsøkt)

Server peker på web-root vs dist-root (blander gamle/ny)

index.html refererer feil til assets (f.eks gammel app.js)

Dette gjør det vanskelig å vite om “LIMITED SIGNAL” endringen faktisk kommer fra siste kode eller gammel.

7) Hva vi har forsøkt for å fikse akkurat nå (tiltak rettet mot A og B)
7.1 Endret data_loader.js for “window-aware + cache + manifest”

Innførte:

loadManifest() -> /data/manifest.json

loadGoldWindow(chain, days) og loadMetaWindow(chain, days) med korrekt filmapping

SESSION_BUST = Date.now() for å unngå caching av fetch

map fra 30/90/180 -> last30d.json/last90d.json/last180d.json og støtte for history/latest

Mål:

Sikre at vi faktisk laster riktig fil og riktig window.

7.2 Endret chain.js for at window-knappene faktisk påvirker data og stats

Når bruker velger 30/90/180:

last riktig gold/meta window

rendrer chart

oppdaterer “Latest/Change/Rolling/Position” basert på valgt window

Mål:

Ikke være “låst” til 30d.

7.3 Endret landing.js for å håndtere regime/policy vs confidence

Forsøkte å introdusere en klar separasjon:

“Regime” = kan være withheld selv om confidence er høy

“LIMITED SIGNAL” = regime withheld, men data/driver/charts kan fortsatt brukes

La inn “What is this?” hint for å forklare LIMITED SIGNAL

Mål:

Unngå at Base/Arbitrum fremstår som “manglende data” dersom data faktisk finnes.

7.4 Build.py ble forbedret for assets-kopi og JSON-sanitization

Sikrer dist/assets/css/styles.css eksisterer etter build

Sanitiserer NaN i JSON så browser ikke krasjer

Opprettholder korrekt kopiering av assets og index

Mål:

Stabil bygg og korrekt UI last.

9) Hva som er neste trinn (konkret plan)

Dette er det du skal gi til ny chat som “nå må vi gjøre dette”:

Trinn 1 — Eliminér versjonsforvirring (kritisk først)

Mål: 100% sikkert at nettleser kjører de nyeste filene.

Tiltak:

Bestem én root som serveren alltid bruker:

enten web/ eller web/dist/

anbefalt: web/dist/ for å speile produksjon

I index.html, legg ALLTID inn ?v=<BUILD> på alle JS/CSS imports:

assets/css/styles.css?v=...

assets/js/app.js?v=...

etc

Hard refresh i browser eller åpne i incognito.

Suksesskriterium:

Bytter du én tekststreng i landing.js, ser du det umiddelbart.

Trinn 2 — Avklar definisjonen av “confidence” vs “regime”

Mål: UI skal ikke si “low confidence” når confidence=100%.

Tiltak:

Innfør to separate scores:

data_confidence (dekning/kvalitet på input)

regime_confidence eller publish_confidence (tillatt å publisere regime)

Oppdater landing.js og chain.js til å bruke korrekt score for riktig tekst.

Suksesskriterium:

Base/Arbitrum kan ha høy data_confidence men fortsatt withheld regime (LIMITED SIGNAL) uten sprik i forklaring.

Trinn 3 — Verifiser faktisk historikk og n i browser

Mål: Bevise at base/arbitrum faktisk har samme antall punkter i window/historikk som BTC/ETH.

Tiltak:

Logg i console:

antall datapunkter i gold/meta for base/arbitrum på 30/90/180

Hvis n er lav i browser:

data_loader peker feil fil (f.eks last30d finnes men last90d/180 finnes ikke)

eller build kopierer bare “latest” og ikke historikk

Suksesskriterium:

window 180 gir >180 punkter (eller nær), og chart endrer seg.

Trinn 4 — Oppdatér “Market overview” regime labels

Mål: Ikke bruke “UNKNOWN/DEGRADED” når det egentlig er “regime withheld”.

Tiltak:

Standardiser:

UNKNOWN/DEGRADED brukes kun når data faktisk mangler / parsefeiler / n under minimum.

LIMITED SIGNAL brukes når data finnes men produktpolicy hindrer regime.

Suksesskriterium:

Base/Arbitrum aldri “DEGRADED” dersom historikk finnes og JSON er ok.
