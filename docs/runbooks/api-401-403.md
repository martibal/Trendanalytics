# API 401 and 403 Runbook

## Purpose

This runbook describes how to diagnose and recover API requests that return 401 or 403 for Urd Atlas authenticated JSON delivery.

## Use this runbook when

- A customer reports that an API request fails with 401.
- A customer reports that an API request fails with 403.
- A customer says their API key worked before but now fails.
- A customer can see an active subscription but cannot access an expected file.
- Support needs to determine whether the issue is authentication, entitlement, chain scope, window scope, subscription state, or key state.

## Safety rules

- Never ask the customer to send a full API key.
- Never paste full API keys into chat, tickets, commits, screenshots, or logs.
- Use only safe identifiers such as account email, key prefix, visible suffix, creation time, or last-used timestamp.
- If a full API key is exposed, use the API Key Rotation Runbook.
- Do not manually widen entitlement until Stripe subscription state and plan scope are verified.
- Do not tell the customer to use Authorization Bearer. The documented authentication header is X-API-Key.

## Expected authentication format

API requests must use:

```http
X-API-Key: <api-key>
```

The following is not the documented authentication method:

```http
Authorization: Bearer <api-key>
```

If the customer is using Authorization Bearer, ask them to retest with X-API-Key before investigating entitlement.

## Step 1 — Classify the response

Record:

- Request URL.
- HTTP status.
- Response body or error code.
- Customer account email.
- Safe key identifier.
- Requested genre.
- Requested chain.
- Requested window.
- Time of request.
- Whether the request was made from the customer's environment or from support verification.

Interpret common statuses:

- 200 means the key and entitlement work for that file.
- 401 usually means missing, malformed, unknown, expired, or revoked API key.
- 403 usually means the key is known but access is not allowed for the requested file.
- 404 usually means the requested file path, genre, chain, or window is not available.

## Step 2 — Diagnose 401

For a 401 response, check:

- The request includes X-API-Key.
- The API key was not truncated.
- The API key has not been revoked.
- The API key belongs to the expected customer account.
- The API key hash or safe identifier exists in the database.
- The customer did not confuse an old key with a newly created key.
- The customer did not copy whitespace, quotes, or shell formatting into the key.

Recovery options:

- Ask the customer to create a new API key from the dashboard.
- Revoke any exposed or suspicious old key.
- Ask the customer to retest using X-API-Key.
- Confirm the new key appears active in the dashboard.

## Step 3 — Diagnose 403

For a 403 response, check:

- Subscription status is active when paid access is expected.
- Entitlement tier matches the purchased plan.
- Entitled chain matches the requested chain.
- Requested window is included in the plan.
- Requested genre is included in the plan.
- API key is active and not suspended.
- Account state has not been canceled, refunded, or downgraded.
- Stripe state and Urd Atlas entitlement state agree.

Common valid 403 cases:

- Customer has Bitcoin-only access but requests Ethereum.
- Customer has a plan that allows 30d or 90d windows but requests 180d or 365d.
- Customer subscription has been canceled immediately.
- Customer has been refunded and access should not remain active.
- Key is active but subscription is inactive.

## Step 4 — Verify with known-good paths

When support verifies access, test one path that should be allowed and one path that should be denied.

Allowed example pattern:

```text
/api/v1/files/gold/<entitled-chain>/latest.json
```

If the plan includes windows, test an allowed window:

```text
/api/v1/files/gold/<entitled-chain>/30d/latest.json
```

Denied example pattern:

```text
/api/v1/files/gold/<non-entitled-chain>/latest.json
```

If the customer requests an out-of-plan window, confirm the 403 is expected rather than an incident.

## Step 5 — Check account and subscription state

If a request appears incorrectly denied, check:

- Customer account exists.
- Stripe customer ID is linked to the account.
- Stripe subscription ID is linked to the account or entitlement record.
- Subscription status is active when Stripe says it should be active.
- Entitlement plan, chain, and window limits match the purchased product.
- Webhook event that should have updated access returned 200.
- No stale processing state remains from a prior failed webhook.

If Stripe shows payment/subscription success but entitlement is missing, use the Paid but No Access Runbook.

If a relevant Stripe webhook returned 500, use the Stripe Webhook 500 Runbook.

## Step 6 — Customer response

For 401, tell the customer:

- The request was not authenticated successfully.
- They should create or use an active API key from the dashboard.
- They must send the key with X-API-Key.
- They should not send the full key to support.

For 403, tell the customer:

- The API key was recognized but the requested file was not allowed by the current entitlement.
- Which plan, chain, or window appears to be active, if safe to share.
- Which request path they should test next.
- Whether support is still investigating a mismatch.

Do not include internal database IDs, full API keys, Stripe secrets, or webhook secrets in the reply.

## Completion checklist

- [ ] Request URL, status, and requested file scope were recorded.
- [ ] Customer API key was not exposed.
- [ ] Authentication header was confirmed as X-API-Key.
- [ ] 401 or 403 was classified correctly.
- [ ] Key state was checked.
- [ ] Subscription state was checked.
- [ ] Entitlement chain/window/genre scope was checked.
- [ ] At least one allowed request was tested, if applicable.
- [ ] At least one denied out-of-scope request was tested, if applicable.
- [ ] Related runbook was used if the issue was paid-but-no-access or webhook 500.
- [ ] Customer reply included no full API keys, secrets, or internal IDs.
